## Phase 3 — Events & live production
**Status: code complete, with one deliberate deviation from the PRD's data model**

### What's built
`events`, `event_crew`, `event_schedule` (`MIGRATION_SQL_P3`), then `event_people` (speakers/guests/moderators/performers) and `attendees` with CSV import (`MIGRATION_SQL_P3B`, run after P3). Events list + detail page (crew, run-of-show, speakers/guests, attendee check-in), and a full-screen mobile "Go Live" view (`EventLivePage`) for day-of run-of-show — tap a segment to cycle pending → live → done.

**Deviation from the PRD/original plan:** the PRD (and the original version of this document) specified `vendors` should ship in Phase 3 specifically to avoid a sequencing conflict — events referencing vendors before vendors exist. In practice, `vendors` shipped in the Phase 4 migration instead, and there is currently no vendor↔event link (`event_vendors` from the PRD's data model was never built — only `project_vendors`, linking vendors to projects, exists). This isn't causing an active bug today since nothing references a vendor from an event row, but if event↔vendor linkage is wanted later, it needs its own small migration addendum.

**Phase 3 acceptance criteria:**
- [ ] One real BTE event fully loaded (event → project link, run-of-show, speakers/guests, attendees) ← founder data entry, blocked on Phase 3 + 3b migrations being run
- [x] Run-of-show usable on a phone — verify on an actual device, not just at 390px in devtools

## Phase 4 — Money out + people ops + roles
**Status: code complete — RLS now enforced for the coarse-grained roles; row-level nuances still need founder sign-off**

### What's built
`profiles`, `vendors`, `purchase_orders`, `payroll_entries`, `project_assignments`, `project_vendors` (`MIGRATION_SQL_P4`), plus `v_staff_load`. Payroll page with WHT auto-computed from staff contract type. Vendors & POs page (orders + directory tabs, 10 seed vendors). Project detail page gained team-assignment and vendor-engagement sections. Staff detail page shows project load. Settings page has founder-only role assignment.

**RLS hardening (`MIGRATION_SQL_P4_SECURITY`, run after Phase 4):** the original Phase 4 migration's RLS policies were `FOR ALL TO authenticated USING (true)` — i.e. any signed-in user, regardless of role, could read/write payroll and finance data directly via the Supabase API; the `Role`/`PAGE_ACCESS` system only ever hid nav items in the UI. This migration replaces those policies to match what `PAGE_ACCESS` already implies in the UI (founder + ops_lead for finance/vendors/targets, founder-only for payroll). **It intentionally does not implement the PRD §8 row-level nuances** — "team lead: full access within own pillar only", "member: read/update own tasks only" — since the PRD itself says that matrix needs founder confirmation before being built, and those tables (`projects`, `tasks`, etc.) still use the original "any authenticated user" policy.

**Before Phase 4 can be considered founder-signed-off:**
- Confirm the PRD §8 permission matrix (or amend it) so the row-level nuances above can be implemented
- Confirm WHT rates by contractor type with the accountant (the app currently defaults to 0% for core staff, 5% for contractor/freelancer/ACE collective — `WHT_DEFAULTS` in code — pending confirmation)
- Replace the 10 seeded placeholder vendors with real ones (≥ 10 real, per acceptance criteria)

**Phase 4 acceptance criteria:**

## Known constraints

- **Edge function resets:** Figma Make reverts `supabase/functions/server/index.tsx` to a stub on every save. All backend logic must go in the React app or directly in Postgres (triggers, functions, views). No pg_cron-based automation is realistic to set up this way — anything time-based needs a client-side computed workaround instead (see the invoice overdue handling above).
- **No service-role key in client code** — all writes go through the Supabase anon key with RLS enforcing access. As of the Phase 4b migration, RLS actually enforces role restrictions on finance/payroll/vendor tables — not just the UI.
- **Single file architecture** — the entire app lives in `src/app/App.tsx` due to Make platform constraints. Split into logical sections with `// ─── Section ───` comment dividers. Each phase's migration SQL is its own `MIGRATION_SQL_P*` constant with a matching `P*SetupBanner` component — follow that pattern for any future phase.
- **No `tsconfig.json`** — the project has no dedicated TypeScript config; Vite/esbuild transpiles without type-checking. `utils/supabase/types.ts`'s `Database` generic only covers Phase 1 tables, so Phase 2–4 table calls are effectively untyped. This doesn't affect the running app but means a strict `tsc` run reports many false-positive "never" errors — that's expected given the current setup, not a sign of broken code.
- **Currency:** Naira only, via `formatNaira()`. Never use `toFixed(2)` directly anywhere else.
- **Dates:** via `formatDate()` only. Display as `DD Month YYYY`.
- **Concurrent editing:** more than one Claude Code session/window has been observed editing `App.tsx` at the same time with no commit boundary between them. Commit frequently to create recovery points, and check `git status`/`git diff` before assuming you know the current state of the file.
